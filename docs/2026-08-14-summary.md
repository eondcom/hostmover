## 무슨 일이 있었나 (시간 순)

1. **신고**: 고객이 `neosol.co.kr`·`sclink.co.kr` 접속 불안정 호소.
2. **1차 원인(웹 스택)**: 크롤러 봇(GPTBot·MJ12bot·Baiduspider 등)이 무거운 게시판 페이지를 반복 요청 → Apache `MaxRequestWorkers=150`이 상시 포화 → nginx가 백엔드 타임아웃.
   → **조치**: 봇 UA 차단 83개 도메인 적용, Apache 워커 상한 150→400, `haebyeong.com` 등 반복 조회.
3. **별도 사고**: `allofhani.com`이 `45.38.0.0/16`·`45.39.0.0/16`(미국 대역) 분산 플러딩에 노출 — 최근 에러로그의 99%가 이 대역.
   → **조치**: 해당 IP 대역 서버 전체 차단.
4. **2차 원인(DB)**: 웹 스택 조치 후에도 "DB 재시작하면 빨라짐" 보고 → 조사 결과 `*_counter_log`(방문자 로그) 테이블이 정리 없이 최대 1,760만 행까지 비대해졌고 대부분 **MyISAM(테이블 단위 락)** — 새벽 백업의 `SELECT *`가 19초·2.7GB씩 테이블을 잠그며 동시 INSERT를 막고, 이게 하루 종일 누적되다 재시작으로만 풀리는 재발성 문제였음.
   → **조치**: `ALTER TABLE ... ENGINE=InnoDB`로 전환(데이터 삭제 없음, 락 단위만 테이블→행으로 변경). 파일럿(우선순위 13개) → 근본 원인이 `*_documents`(게시글) 테이블에도 있음을 추가 확인해 29개 더 전환 → 그래도 남은 **서버 전체 MyISAM 3,193개**를 33개 DB 단위로 일괄 전환. 최종 **서버 전체 MyISAM 테이블 0개**, `Table_locks_waited` 초당 3.75건 → 사실상 0건.
5. **용량 관리(부가 과제)**: 락 경합은 해결됐지만 `*_counter_log`가 계속 커지는 근본 문제(백업 시간, 디스크)는 남아있어 별도로 처리:
   집계(월별 요약 테이블) + 아카이브(오래된 상세 행을 `ARCHIVE` 엔진 테이블로 압축 이관, 원본은 최근 3개월만 유지) 설계 → `hb_counter_log`로 파일럿 검증(버그 2건 발견·수정: 예약어 컬럼명, 미설치 ARCHIVE 엔진) → 나머지 12개 배치 적용(버그 1건 추가 발견·수정: 테이블마다 다른 컬럼 순서) → 서버 전체 재조사로 빠졌던 13개 추가 적용(`eond_eond`는 사용자 지시로 제외).

## 아직 안 끝난 것

- `eond_eond.xe_counter_log`(1,035MB) — 필요 시 별도 진행.
- 봇 차단 훅이 없는 구형 템플릿 9개 도메인(`aiui.kr` 등) — 필요 시 별도 진행.
- counter_log archive 데이터의 관리자 화면 조회 경로, 고객 고지 여부 — 미결정.
- 며칠간 관찰: 특히 핫 테이블이 0행이 된 곳(`eond_yncare`·`itmang_itmang`·`oracall_dev`·`eond_aithres`)이 XE 관리자 화면에서 이상 없이 보이는지.
- 재발 방지책(XE 신규 설치 시 기본 InnoDB, 백업 전략 재검토)은 설계만 되어 있고 미실행.
